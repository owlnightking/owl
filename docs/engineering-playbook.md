# 软件迭代手册（Engineering Playbook）

> 适用：Owl 仓库（api-service / cron-service / 五个前端）与后续 SaaS 化改造。
> 约束前提：研发 1-3 人，业务与研发同批人，系统必须服务真实经营而不是演示。
> **范围与顺序以 `docs/implementation-plan.md`（P1–P4）为准**；本手册只讲"怎么排期与验收"，不定义做什么。

---

## 一、总原则

| 原则               | 含义                                              | 反例                                 |
| ------------------ | ------------------------------------------------- | ------------------------------------ |
| 单轨开发           | 只维护 `main` 一条长期分支，短分支存活不超过 2 天 | 开三个 feature 分支并行三个月        |
| 双周一个可上线单元 | 每两周必须有东西真正跑在自己的经营里              | 一个模块做两个月才第一次打开页面     |
| 数据先于界面       | 先让一条真实数据端到端跑通，再做列表页和筛选器    | 先做十个管理页面，数据靠 mock        |
| 一次只开一个模块   | 同一时间只有一个 P0 模块在开发                    | 利润引擎、内容工厂、渠道中枢同时开工 |
| 真实数据验收       | 用自己的真实 SKU、真实订单验收                    | 造演示数据截图交差                   |
| 可回滚优先         | 任何上线都必须能在 10 分钟内回到上一版            | 大改表结构且没有备份                 |

**一句话**：小团队的优势是决策快，唯一的敌人是"同时做太多"和"做完不验收"。

## 二、迭代节奏

### 2.1 双层节奏：双周迭代 + 季度架构复盘

```
双周迭代（Sprint）
  D1  周一  规划 30 分钟：定 1-3 个目标（不是任务清单）
  D2-D9     开发，每日站会 15 分钟
  D9  周四  自测 + verify:quick + 真实数据跑一遍
  D10 周五  Demo（用真实经营数据演示）→ 15 分钟复盘 → 合并发版
季度
  季度末  架构复盘：ADR 增补、债务清理、下季度路线校准
```

### 2.2 为什么是双周而不是一周

- 一周做不完"数据模型 + 迁移 + 接口 + 页面 + 单测"的完整闭环，会退化成只做页面；
- 一个月又太长，反馈不及时，业务侧等不起。
- 双周刚好等于"一个业务验证周期"（测投、上新、复盘），研发节奏与经营节奏对齐。

### 2.3 创始人同时管业务时的日历切分

| 时段       | 角色           | 原则                                   |
| ---------- | -------------- | -------------------------------------- |
| 周一、周二 | 业务日         | 不写代码，只处理渠道、供应链、政策申报 |
| 周三至周五 | 研发日         | 不做业务决策，只推进当前迭代目标       |
| 周末       | 禁止加班写代码 | 小团队靠可持续节奏，不靠冲刺           |

这条看似与工程无关，实际是最重要的一条：**混杂日程是 1-2 人团队最大的效率杀手**。

## 三、需求怎么进来（唯一入口）

### 3.1 需求来源只有一个：经营痛点

需求必须来自月度经营分析会（见 `operating-plan.md` 第九节），格式固定：

```
痛点卡
- 谁：运营 / 供应链 / 我自己
- 什么时候：每周五做月报时
- 现在怎么做：导出 4 个平台 Excel，手工拼，3 小时
- 损失：每月 12 小时 + 算错一次导致压货 8 万
- 期望：打开就能看到每个 SKU 的真实毛利
- 验收：与财务月报差异 < 2%
```

没有这张卡的，不排期。**"竞品有这个功能"不是需求。**

### 3.2 优先级规则（不靠感觉排序）

> 下表 P0–P2 是**优先级**，与实施期次 P1–P4 无关；期次以 `docs/implementation-plan.md` 为准。

| 级别 | 判定                                                     | 排期       |
| ---- | -------------------------------------------------------- | ---------- |
| P0   | 直接影响现金流或决策正确性（利润、库存、回款、内容产能） | 当期       |
| P1   | 显著省时间（每周省 2 小时以上）                          | 下期       |
| P2   | 体验优化、报表美化、权限细化                             | 有剩余工时 |
| 不做 | 与 P1–P4 范围无关，且不产生现金流/合规价值               | 进冻结清单 |

### 3.3 需求池上限

**同时存在的"待做"条目不超过 12 条。** 超过就说明没有取舍，直接把最旧的 3 条删掉（不是归档，是删除）。

## 四、一个功能从想法到上线：七步

| 步骤               | 产出                                                           | 通过标准                                                |
| ------------------ | -------------------------------------------------------------- | ------------------------------------------------------- |
| 1. 痛点卡          | 一张卡（见上）                                                 | 有量化损失                                              |
| 2. ADR             | `docs/decisions/NNN-*.md`：背景/决策/后果/关联                 | 写清"为什么不做另一个方案"                              |
| 3. 数据模型        | Prisma schema 变更 + 迁移文件                                  | 自增 id、软删除、createdAt/updatedAt、tenant_id（新表） |
| 4. 骨架贯通        | 一条数据端到端：DTO → Controller → Service → Repository → 页面 | 能在页面看到一条真实记录                                |
| 5. 真实数据接入    | 用自己一个真实 SKU / 一个真实订单跑通                          | 数字与平台后台一致                                      |
| 6. 测试与门禁      | 单测（成功 + 失败路径）、`pnpm verify:quick`                   | 全绿                                                    |
| 7. 上线自用 + 复盘 | 用满 3 个工作日，记录"是否真的省了时间"                        | 省时数据写回痛点卡                                      |

### 4.1 完成定义（DoD）

一个功能算"完成"，必须同时满足：

- 真实数据跑通，不是 mock；
- application 层有单测，覆盖成功与至少一条失败路径；
- 权限点已注册（新页面/按钮进 RBAC）；
- 关键写操作进审计日志；
- 接口有 Swagger 注解与中文描述；
- `pnpm verify:quick` 全绿（typecheck / lint / format / arch / doc / business / feature / frontend / backend / test）；
- `PROJECT_STATE.md` 与 `business-snapshot.md` 同 commit 更新（仓库既有规则）；
- 有一条"如果错了怎么发现"的监控或核对手段。

### 4.2 分段交付示例：P1-1 权限码表单源

不要一次做完，按四段交付，每段都可独立验收：

| 段  | 内容                                        | 可验收点                                   |
| --- | ------------------------------------------- | ------------------------------------------ |
| 1   | `packages/permission` 注册表 + 种子幂等同步 | 权限表与注册表一致，旧码软删除             |
| 2   | 后端装饰器改用注册表常量 + 补齐缺失接口校验 | 未授权账号调用主链接口返回 403             |
| 3   | 前端菜单/路由守卫/按钮组件统一取码          | admin 全菜单可见，普通员工仅授权菜单       |
| 4   | 超管 bypass + Redis 缓存 + 变更失效 + 单测  | 改角色后 10s 内生效，单测覆盖成功/失败路径 |

**关键**：第 2 段先只做「接口拒绝」，不要等前端全部改完；后端先形成真实防线，前端再逐步收敛。

## 五、架构怎么演进（三阶段，有明确触发条件）

### 5.1 阶段一：模块化单体 + 租户预留（现在至 2028 Q1）

| 做法                                      | 说明                                                |
| ----------------------------------------- | --------------------------------------------------- |
| 单体部署                                  | api-service / cron-service 各一个进程，不拆服务     |
| 新表带 `tenant_id INT NOT NULL DEFAULT 1` | profit / content / channel 全部带；老表不动         |
| 读写收敛在 repository                     | 禁止 Controller 直连 Prisma（仓库已有规则）         |
| 不引入新中间件                            | 复用现有 Postgres / Redis / RabbitMQ / MinIO        |
| 平台接入走适配层                          | 统一 `ChannelAdapter` 接口，平台差异只在 adapter 内 |

**为什么新表先带 tenant_id**：加一列的成本是 1 天，事后给 40 张表补列 + 回填 + 改所有查询的成本是 2-3 周，而且容易漏。这是一次性买保险。

### 5.2 阶段二：租户上下文（2028 Q2，SaaS 闸门通过后才做）

| 动作             | 顺序                                                                |
| ---------------- | ------------------------------------------------------------------- |
| 请求级租户上下文 | 中间件解析租户 → 注入请求作用域 → 仓储层强制过滤                    |
| 老表迁移         | expand（加列可空）→ migrate（回填）→ contract（加 NOT NULL + 索引） |
| 隔离测试         | 每个租户跑一份数据，交叉查询必须查不到                              |
| 开通流程         | 建租户 → 初始化种子 → 发账号                                        |

**红线**：租户过滤必须在仓储层统一做，不允许各业务代码手写 `where tenantId`——漏一处就是数据泄露。

### 5.3 阶段三：按需拆分（2028 Q4 之后，且必须满足触发条件）

只有满足以下任一条件才拆服务：

- 单表超过 5000 万行，或单查询 P95 > 800ms 且索引优化无效；
- 同步任务与在线请求互相拖垮（队列积压影响接口响应）；
- 团队超过 6 名研发，部署冲突每周超过 1 次。

拆分顺序：**先拆离线任务（渠道同步、AI 批处理），再考虑拆在线服务**。核心 CRUD 永远最后动，甚至不动。

### 5.4 技术选型纪律

| 场景      | 用什么                       | 不用什么                            |
| --------- | ---------------------------- | ----------------------------------- |
| 定时任务  | 现有 cron-service + 任务表   | 新引入调度框架                      |
| 异步/重试 | 现有 RabbitMQ                | Kafka（数据量级不需要）             |
| 缓存      | 现有 Redis                   | 多级缓存框架                        |
| 报表      | Postgres 物化视图 + 定时刷新 | 数据仓库 / BI 平台（第 3 年再评估） |
| 前端图表  | Arco 生态 + 轻量图表库       | 自建可视化框架                      |
| 支付      | 第三方（支付宝/微信/Stripe） | 自研结算                            |

## 六、渠道集成怎么迭代（最容易拖垮项目的一块）

### 6.1 一个月接一个平台，顺序固定

| 顺序 | 平台             | 理由                     | 周期 |
| ---- | ---------------- | ------------------------ | ---- |
| 1    | Amazon（SP-API） | 收入占比最高，接口成熟   | 3 周 |
| 2    | 抖店开放平台     | 国内业务验证快           | 2 周 |
| 3    | TikTok Shop      | 增量渠道，接口较新需多测 | 3 周 |
| 4    | Shopify          | 接口最简单，最后做       | 1 周 |

**禁止**：四个平台同时接入。适配层的价值就在于"一个一个接，接完一个就稳定一个"。

### 6.2 分层结构

```
channel_raw（原始表，永不删、永不改）
    ↓ 归一化任务（按平台 adapter）
channel_order_fact（订单事实表）
    ↓
profit（成本与利润计算）
    ↓
content（素材与投放回传）
```

- 原始表保留原始 JSON：平台改字段、口径争议、对账差异，都能回到原始数据查；
- 事实表只存归一后的字段，所有下游只读事实表；
- 任何"数据不对"的问题，先看 raw 有没有，再看归一规则，最后看计算逻辑——三层定位，不猜。

### 6.3 同步机制（必须一次做对的三件事）

| 机制   | 做法                                                               |
| ------ | ------------------------------------------------------------------ |
| 水位线 | `sync_watermark(platform, resource, last_sync_at)`，每次只增量拉取 |
| 幂等键 | `platform + order_no + version`，重复拉取不产生重复数据            |
| 补数   | 按时间窗重跑，支持指定日期区间；失败自动重试（指数退避）           |

### 6.4 验收标准（对账，不是"看起来有数据"）

- 每日自动对账：系统订单数 / 金额 vs 平台后台，差异率 < 0.5%；
- 差异必须能定位到具体订单号，不能只给一个总数；
- 连续 7 天无差异，才算该平台接入完成。

### 6.5 限流与稳定性

- 令牌桶限流，单平台配额用满前 20% 预留；
- 单平台故障不影响其他渠道（适配层隔离 + 独立重试队列）；
- 同步任务写运行日志（成功/失败/耗时/条数），异常进 `system_log`。

## 七、AI 功能怎么迭代（内容工厂特有）

AI 功能最大的陷阱是"看起来变好了"，所以必须工程化。

### 7.1 三件套：Prompt 版本化 + 评测集 + 成本台账

| 项            | 做法                                                             |
| ------------- | ---------------------------------------------------------------- |
| Prompt 版本化 | prompt 存库，带版本号与用途标签，可回滚；不写在代码字符串里      |
| 评测集        | 20-50 条真实样本 + 人工打分（可用性 1-5 分），每次改 prompt 必跑 |
| 成本台账      | 每次调用记录 token 与费用，按"单条素材成本"汇总，超阈值告警      |

### 7.2 上线标准

- 评测集平均分不低于上一版，且无样本跌破 3 分；
- 单条素材成本不超过目标值（第 1 年 ≤ 60 元）；
- 有失败兜底：模型超时或报错时降级到模板脚本，不阻断生产。

### 7.3 不做的事

- 不训练自己的大模型（成本与收益不匹配）；
- 不做"一键全自动成片"（质量不可控，返工成本更高）；
- 不用"生成得像不像"作为验收标准，用"投放后有没有转化"。

## 八、发布与回滚

| 环节     | 做法                                                                    |
| -------- | ----------------------------------------------------------------------- |
| 分支     | 短分支（< 2 天）→ PR → 合并 `main`                                      |
| 门禁     | pre-commit（增量扫描）+ pre-push（`pnpm verify:quick`）+ CD（版本门禁） |
| 发版节奏 | 每周五一次；改 schema 的必须与代码同一个 PR                             |
| 迁移策略 | expand → migrate → contract（只加不删；删列延后一版）                   |
| 灰度     | 内部自用 3 天 → 再给内测客户（SaaS 阶段引入开关）                       |
| 回滚     | 镜像 tag 回滚 + 数据库向前兼容；回滚时间目标 10 分钟                    |
| 备份     | 每日自动备份；每季度做一次恢复演练（真恢复到临时库）                    |

**数据库红线**：禁止 `migrate reset`、禁止 `db push --accept-data-loss`（仓库已有规定，属于共享库）。

## 九、质量门禁（沿用仓库，补三条）

仓库已有：`typecheck / lint / format / arch / doc / business / feature / frontend / backend / test`，`pnpm verify:quick` 为唯一权威入口。

补充三条团队内规则：

1. **新模块必须有 `.spec.ts`**：至少覆盖成功路径 + 一条失败路径；无单测不算完成。
2. **每个模块一个 owner**：谁写谁维护，跨模块改动必须 owner 知情。
3. **季度灾备演练**：从备份恢复一次，验证能否在 30 分钟内回到可用状态。

### 技术债管理

| 类型                        | 处理                                                |
| --------------------------- | --------------------------------------------------- |
| 阻断型（影响数据正确/安全） | 当迭代内解决，不排期                                |
| 成本型（每次改动多花时间）  | 进 `PROJECT_STATE.md` 已知缺口，每迭代预留 20% 工时 |
| 美观型（命名、注释、格式）  | 不做，交给自动格式化                                |

## 十、反模式（踩过的和会踩的）

| 反模式                   | 后果                     | 替代做法                   |
| ------------------------ | ------------------------ | -------------------------- |
| 同时开三个模块           | 三个都做不完，全部延期   | 一次一个 P0                |
| 先做后台管理页           | 页面漂亮但数据不对       | 先跑通一条真实数据         |
| 为演示造假数据           | 评审/客户一验证就崩      | 用真实数据，哪怕难看       |
| 大重构                   | 两周不动业务，回归风险高 | 小步替换，旧逻辑保留开关   |
| 过早多租户               | 半年没上线，需求已变     | 新表带 tenant_id，老表后补 |
| 过度抽象                 | 一个功能五个接口层       | 一个模块三层，够用即止     |
| 用 UI 打磨代替数据准确性 | 决策依据错误             | 先对账，再美化             |
| 没有验收标准就开工       | 做完不知道算不算完成     | 痛点卡必须写验收条件       |

## 十一、第一个迭代的具体样子（2026 Q4 前两周）

**目标**：利润引擎第一段（成本归集 + 汇率快照），让一个真实 SKU 的落地成本可查。

| 日    | 动作                                                       | 产出             |
| ----- | ---------------------------------------------------------- | ---------------- |
| D1    | 写 ADR 013（利润引擎决策）+ 痛点卡                         | ADR 文件         |
| D2    | 设计 schema：`cost_batch`、`fx_snapshot`、`sku_cost_daily` | Prisma 迁移      |
| D3    | 迁移 + repository + service 骨架                           | 一条数据写入成功 |
| D4-D5 | 采购报价录入接口 + 页面（含汇率展示）                      | 能录一条真实报价 |
| D6    | 头程费用录入                                               | 落地成本可算     |
| D7    | 单测（成功 + 币种缺失失败）                                | spec 通过        |
| D8    | 用自己的真实 SKU 跑通，核对人工计算结果                    | 数字一致         |
| D9    | `pnpm verify:quick` + 修复                                 | 全绿             |
| D10   | Demo + 复盘 + 合并                                         | 上线自用         |

**验收**：任意一个在售 SKU，输入报价与头程，能算出人民币落地成本与美元折算成本，且与手工计算一致。

## 十二、迭代健康度指标（每季度自评）

| 指标       | 定义                            | 目标     |
| ---------- | ------------------------------- | -------- |
| 部署频率   | 每周上线次数                    | ≥ 1      |
| 交付周期   | 从痛点卡到上线自用              | ≤ 3 周   |
| 变更失败率 | 上线后 7 天内需回滚或热修的比例 | ≤ 15%    |
| 恢复时间   | 从发现问题到恢复                | ≤ 1 小时 |
| 对账差异率 | 系统与平台/财务的差异           | < 0.5%   |
| 债务占比   | 每迭代用于还债的工时            | 15%-20%  |
