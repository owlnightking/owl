# Owl 项目实施计划（分阶段）

> 基于 `docs/decisions/002-product-positioning-and-roadmap.md` 重排。
> 交付形态：单仓库 monorepo + GitHub Actions CI/CD，5 个应用（api-service / cron-service / owl-web / admin-web / cron-web + mobile-web / portal），K8s 命名空间 `owl`。
> 投入：开发 1-2 人。
> 历史基线：原 Phase 0（工程脚手架）已完成、Phase 1（认证与权限底座）代码基本完成但验收未全勾——见「已完成历史基线」。

## 一、领域地图与总体顺序

| 领域       | 定位                                                                 | 承载                   | 当前状态                      | 顺序              |
| ---------- | -------------------------------------------------------------------- | ---------------------- | ----------------------------- | ----------------- |
| 组织支撑域 | 认可中心、人才中心、智能客服 + 内部知识库、基础配置与监控、协同底座  | admin-web + mobile-web | 需求基线已收敛，未开始        | 先做              |
| 副业域     | 付费知识（md 组件创作的文档库，文本入库、商业化后置）                | mobile-web + admin-web | 需求基线已收敛，**B1 进行中** | 次做（S1 后优先） |
| 主领域     | 自研产品跨境电商业务系统（13 阶段流水线 / 利润聚合，owl-web 工作台） | owl-web + admin-web    | 原规划保留（见 M0）           | 后做              |

### 入口与权限基线（全局）

- 触点按**角色**定义，不按"端"归属；同一角色在不同端（admin / owl / cron / mobile）看到各自被授权的模块与操作。
- RBAC 到**按钮级，四层统一**：菜单可见 → 页面可进 → 按钮可点 → 后端接口校验。
- 初期仅内置**两角色：超管 / 普通员工**（超管兼任运营/HR/客服/内容等职能），角色后续再拆分。
- mobile 全员可见；审批类按钮只在超管（管理角色）的消息流里出现。
- 登录：本地开发用可切换任意用户/角色的 mock 通道；生产走真实飞书 OAuth。
- 内站消息 MVP 用轮询（30~60s 拉未读/列表），接口预留实时推送升级位。
- 默认落地端范围：里程碑按「admin + mobile」两端推进；owl-web 近期仅做角色裁剪下的可见性，不新接支撑域模块；cron 保留现有任务中心基础。

## 二、已完成历史基线（保留摘要）

### Phase 0：工程脚手架（已完成）

monorepo / pnpm workspaces / 工程护栏（typecheck、lint、format、arch、AI 残渣扫描、特征规则、文档新鲜度）/ 本机 docker 中间件复用（PostgreSQL / Redis / RabbitMQ / MinIO）/ CI-CD（cd.yml，版本门禁）/ 各前端骨架。验收见原文档，均已达标（除 "提交 GitHub 触发 ci 全绿" 待验证）。

### Phase 1：认证与权限底座（代码基本完成，验收未全勾）

- auth：飞书 OAuth 登录、JWT 双 token 无感刷新、Redis 会话与黑名单、SSO
- user / role / audit-log / field-config：完整实现 + admin 页面
- 未完成验收项：单测覆盖低、本地飞书 SSO 未配置真跑

### S0：支撑域底座（已完成）

- PrismaClient 全局单例（DATABASE_CLIENT token + DatabaseProvider）
- system-config 模块：CRUD + Redis 缓存（300s TTL）
- permission 模块：CRUD + @RequirePermission 权限守卫
- notification 模块：CRUD + 未读计数 + 全部已读
- file 模块：元数据 CRUD（MinIO 集成待后续补全）
- admin 菜单：二级分组 + 权限过滤渲染
- mock 登录通道：GET /auth/mock-users + POST /auth/mock-login（非生产环境）
- /auth/me 返回 permissions 数组

## 三、需求基线（已与业务逐题确认）

### 组织支撑域 · 认可中心（里程碑 1，见 S1）

| 环节      | 规则                                                                                                             |
| --------- | ---------------------------------------------------------------------------------------------------------------- |
| 认可贴    | 员工 mobile 发起（被认可人 + 徽章 + 留言）→ 生成待审批认可消息推送超管 → 超管通过/驳回 → 通过进全员 Feed，可置顶 |
| 产币      | 仅认可贴审批通过产币：被认可人获固定币（后台可配）+ 经验；普通点赞不产币                                         |
| 体力/防刷 | 点赞消耗发起者体力（每月重置、上限可配）；同人对同一认可贴限赞 1 次                                              |
| 徽章      | admin CRUD；徽章图走文件服务上传                                                                                 |
| 兑换      | 员工商城下单即时扣币 → 待审核单 → 超管审核：通过=发货/领取核销并减库存；驳回=退币                                |
| 商城      | admin 商品上架（名称/图/价格/库存/上下架）                                                                       |
| 等级      | 经验累积升级；超管可调账（补发/扣减币）                                                                          |
| mobile    | 首页 Feed、消息（审批在超管消息流）、商城、我的（币余额/等级经验/体力月重置/发起认可/兑换记录）                  |

### 组织支撑域 · 人才中心（S2）

- 面试信息填写 = 候选人自助采集：候选人连公司 Wi-Fi 扫二维码填表，或填飞书表单；**定时任务将数据同步入库**（复用飞书→系统同步管线）
- 入库生成候选人记录（待处理）→ HR 在 admin 人才中心跟进排面/面试 → 面试官（内部员工）填面试评价与结果 → 通过者转正式员工并建员工档案
- 表单字段由动态字段配置（field-config）驱动；人员管理 / 员工档案以飞书通讯录同步为基础 + HR 维护（入转调离状态、档案扩展）

### 组织支撑域 · 智能客服 + 内部知识库（S3）

- 知识库用途：记录、管理、检索三类内部文档：业务文档 / 系统指南文档 / 组织文档
- 与 AI 配合：admin 配置 LLM API（Key 走 Secret），AI 基于文档库问答，检索范围受提问者可见权限约束；无人工坐席

### 组织支撑域 · 基础配置与监控（S4，可穿插各期）

- 权限 RBAC：补 permission 管理 API，落地按钮级四层权限点与菜单配置
- 操作日志 / 动态字段：已有，随新模块扩展
- 使用统计：平台活跃（各端登录/活跃/操作量趋势）+ 核心业务指标（认可发帖/审批/兑换/币流动/知识库查询）按天聚合看板
- MCP：工具注册表 + 会话 + 调用日志的管理页面与 API（当前表已建、模块空壳）
- 消息推送监控：仅内站消息投递（发送/成功/失败/重试/已读）
- 数据监控：数据同步（SyncLog）+ 业务数据量趋势 + 资源（DB/Redis/MinIO）健康

### 副业域 · 付费知识（B1）

- 同一文档/内容库：移动端与 web 端 **md 组件**创作，正文以数据库字段持久化
- 分类组织、可见权限、商业化（对外售卖/支付入口）均后置，本期只做创作与入库
- mobile「我的」新增 md 编写文档入口即此创作端

### 主领域 · 自研产品跨境电商（M0，远期）

原 13 阶段机会流水线规划保留（见本文档第六节 M0 摘要），作为主领域后续重启时依据。

## 四、开发排期（组织支撑 → 副业 → 主领域）

### 阶段 S0：支撑域底座（前置，里程碑 1 的地基） ✅ 已完成

**目标**：把认可中心需要的横切能力补齐，否则业务长不出来。

1. ✅ **permission 模块填实**：权限点管理 API（resource/action 注册、CRUD）+ 内置两角色种子；按钮级四层校验基建（前端菜单/按钮按权限渲染，后端 @RequirePermission）
2. ✅ **admin 菜单改造**：支持一级分组 + 二级菜单；菜单项由角色权限派生
3. ✅ **notification 模块落地**：内站消息（写库、未读/已读、按用户列表、轮询拉取），业务事件触发发消息的通用入口
4. ✅ **file 模块落地**：MinIO 预签名上传/下载，桶规划（badges/products/...）
5. ✅ **system-config 落地**：字典与可配参数（认可币额、体力上限等）
6. ✅ **本地 mock 登录通道**：可切换任意用户/角色，供验收 RBAC 四层
7. ✅ **PrismaClient 单例收敛**（顺带，属底座债务）

### 阶段 S1：里程碑 1 = 认可中心闭环（admin + mobile）

**目标**：认可闭环跑通并真接移动端。

1. 数据模型：认可徽章（Badge）、认可贴（Recognition + 审批状态/置顶 + 点赞）、币账户/币流水（CoinAccount/CoinTransaction）、体力账户（月度）、兑换单（ExchangeOrder）、兑换商品（Product）、商品库存
2. admin（认可中心）：徽章 CRUD、认可贴审批/置顶、兑换单审核（通过发货核销/驳回退币）、商品上架
3. api-service：recognition 领域模块（发起→审批→Feed→产币；点赞扣体力；兑换扣币/审核/退币/减库存；超管调账）
4. mobile：首页认可 Feed、消息（超管含审批入口）、商城兑换、我的（币/等级/体力/发起认可/兑换记录）——mock 全部替换为真实接口
5. 权限点按两角色预置；移动端超管消息流含审批按钮、普通员工仅见消息

### 阶段 B1：付费知识（副业）

md 编辑组件（web + mobile）+ 文档创作入库 + 列表/编辑/预览，作者可见自己的文档；商业化后续。

### 阶段 S2：人才中心

候选人采集表单（扫码页/飞书表单）→ cron 同步任务入库 → 候选人管理 → 面试安排/面试官回填评价 → 转正建员工档案；人员管理（入转调离）与档案维护。

### 阶段 S3：智能客服 + 内部知识库

知识文档（业务/系统指南/组织）的记录管理检索 + 文档可见权限；LLM API 配置（Secret）；AI 基于文档问答；文档中心页（admin + mobile 查阅入口按需）。

### 阶段 M0：主领域 13 阶段流水线（远期）

按原规划重启，见第六节。

## 六、M0 主领域摘要（原 13 阶段流水线，远期依据）

> 来源：原 implementation-plan Phase 2/3/4 决策集，领域整体后移但需求保留。

1. **核心闭环**：13 阶段单对象线性状态机（机会判断 → 投入验证 → GTM 投流 → 供应链履约 → VOC 售后 → 财务利润测算 → 利润核算 + 投决通过/否决），三段分组（开发验证期/上市执行期/经营层），可回退改数全链重算
2. **利润公式（packages/shared 纯函数）**：利润 = Σ销售额 − Σ广告成本 − Σ产品成本 − Σ履约成本 − 投入成本 − Σ退款额 − Σ售后成本；全生命周期口径，含单测
3. **管道看板（owl-web）**：列表展示当前阶段/投决结果/实时利润/经营状态 + 阶段表单 + 推进历史
4. **验收口径**：创建机会走完全流程、已知数据利润核对、回退重算、否决终态、只读角色限制、E2E 冒烟
5. 依赖底座：project 模块（当前空壳）+ 后续 cron 任务中心用于定时同步
